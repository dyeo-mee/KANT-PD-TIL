# Product Designer를 위한 웹 접근성 가이드
> 웹/앱 접근성의 기준과 디자인 설계 시 고려해야할 점 살펴보기

### 디자이너가 고려해야 할 핵심 항목
| 설계 단계 | 확인할 것 |
|---|---|
| 기획, 사용자 흐름 | 재입력 줄이기, 로그인 대안, 결제/삭제 확인, 시간 연장 |
| 정보구조, 와이어프레임 | 제목 구조, 읽기/초점 순서, 일관된 메뉴 |
| 비주얼, 디자인 시스템 | 대비, 색 외의 단서, 초점 상태, 타깃 크기 |
| 인터랙션, 반응형 | 키보드 조작, 드래그/제스처 대안, 큰 글자와 좁은 화면 |
| 콘텐츠, UX 라이팅 | 대체 텍스트, 라밸, 오류 문구, 링크 문구, 자막 |
| 핸드오프 | 컴포넌트 이름/역할/상태, 상태 메시지 |

**레벨: A는 최소, AA는 일반적인 목표, AAA는 더 강화된 높은 수준의 요구사항.**

### 보조기술의 종류
| 보조 기술 | 주 사용자 | 디자이너가 챙길 것 |
|---|---|---|
| 스크린 리더(VoiceOver, TalkBack, NVDA) | 전맹, 저시력 | 이름, 제목 구조, 읽는 순서, 상태 안내 |
| 점자 정보 단말기 | 전맹, 시청각 중복 장애 | 텍스트 대체, 간결한 레이블 |
| 화면 확대기(Windows 돋보기, ZoomText) | 저시력 | 리플로우, 정보간 거리, 대비 |
| 고대비 모드, 사용자 스타일 확장 도구 | 저시력, 난독 | 색에만 의존하지 않기, 간격 변화 허용 |
| 키보드, 대체 키보드 | 운동 장애, 스크린 리더 사용자 | 초점 순서와 초점 표시 |
| 스위치 장치 | 중증 운동 장애 | 단계 수 줄이기, 시간 제한 없애기 |
| 음성 인식(Voice Control, Dragon) | 손 사용이 어려운 사용자 | 보이는 글자와 같은 이름 |
|헤드 포인터, 시선 추적 | 중증 운동 장애 | 큰 타깃, 드래그 대안 |

## 원칙1. 인식의 용이성
> 눈이나 귀 한가지에만 의존하지 않고 정보가 잘 전달되게 만드는 것이 중요함.

#### 1.1 대체 텍스트
1.1.1 텍스트가 아닌 콘텐츠(A)
- 접근성: 이미지, 아이콘, 차크에는 같은 목적을 전하는 텍스트가 존재해야함.
- 보조 기술: 스크리 리더, 점자 정보 단말기
- 실무 적용
    - 디자인 시안에 "정보형/기능형/장식형"을 표시해 정보형은 기능, 기능형은 동작, 장식형은 '읽지 않음'으로 지정해 소통한다.<br>
    - 차트는 짧은 설명과 함께 데이터 표나 요약문을 설계함.
- 예외 상황
    - 순수 장식용 요소는 보조기술이 무시하도록 처리할 것.
    - 시험 문제나 감각 체험용 콘텐츠는 식별용 설명만 제공하기.
    - CAPTCHA: 사람과 로봇을 구별하는 테스트. 시각 외의 방식도 함께 제공하기.

#### 1.2 시간 기반 미디어
1.2.1/1.2.3/1.2.5 대본과 화면 해설(A/AA/AAA)
- 접근성: 녹음, 무음 영상, 영상 속 시각 정보를 대본이나 음성 해설로도 전달.
- 보조 기술: 스크린 리더, 점자 정보 단말기(대본 읽기)
- 실무 적용
    - 플레이어 바로 아래 '대본 보기'를 배치하기.
    - 영상 기획 단계에서 화면에만 나오는 정보를 나레이션에 포함하기.
- 예외 상황: 미디어가 대체 콘텐츠고 그 내용이 명시돼있어 확인 가능한 경우 제외.
- 예시: 앱 사용법 영상에서 "여기를 누르세요"가 아닌, "오른쪽 아래 저장 버튼을 누르세요"라고 하기.

1.2.2/1.2.4 자막(A/AA)
- 접근성: 녹화 영상과 실시간 방송의 소리 정보를 자막으로 제공.
- 보조 기술: 자막 자체가 청각 장애 사용자의 접근 수단.
- 실무 적용
    - 플레이어에 자막 켜기 버튼과 자막 영역을 설계하기.
    - 화자의 대사뿐 아니라 중요한 효과음도 담기. [문을 닫는 소리],[한숨]
- 예외 상황: 미디어가 본문 텍스트의 대체물이라고 명시된 경우.
- 예시: 라이브 커머스 화면에 실시간 자막 영역을 두고 상품 버튼이 자막을 가리지 않게 설계함.

#### 1.3 적응 가능
1.3.1 정보와 관계(A)
- 접근성: 눈에 보이는 구조(제목, 목록, 표, 라벨 연결)를 코드로도 알 수 있어야 함.
- 보조 기술: 스크린 리더, 점자 정보 단말기
- 실무 적용
    - 텍스트 스타일 이름과 별도로 제목 레벨(H1~H3)을 주석으로 달기.
    - 목록, 표 머리글, 입력 요소, 영역(헤더, 네비게이션, 본문)을 표시.
- 예시: 요금제 비교표에서 '요금제 이름'은 열 머리글, '기능'은 행 머리글로 지정.

1.3.2 의미있는 순서(A)
- 접근성: 순서가 뜻에 영향을 주면 읽는 순서가 올바르게 지정되어야 함.
- 보조 기술: 스크린 리더, 점자 정보 단말기
- 실무 적용
    - 시안 위에 1,2,3 번호로 읽기 순서를 표시하기.
    - 반응형에서 열이 바뀌어도 순서가 유지되는지 확인하기.
- 예외 상황: 순서가 의미에 영향을 주지 않으면 생략.
- 예시: 상품 카드를 '상품명-가격-할인조건-담기' 순으로 읽게 지정.

1.3.3 감각적 특성(A)
- 접근성: 모양, 크기, 위치, 소리 등 하나의 감각만으로 안내하지 않음.
- 보조 기술: 스크린 리더, 음성 제어
- 실무 적용
    - 오류 상태를 빨간색으로만 표현하지 않고 메시지를 함께 제공하기.
    - 버튼과 링크에 명확한 이름을 제공하기.
- 예외 상황: 시각적 표현을 보조적으로 사용하는 것. 문제는 그것만으로 정보를 전달하는 경우.
- 예시: "오른쪽 파란 버튼을 선택하세요" -> "결제하기 버튼을 선택하세요"

1.3.4 화면 방향(AA)
- 접근성: 콘텐츠의 화면표시 및 조작을 세로 또는 가로 한 방향으로 제한하지 않기.
- 보조 기술: 기기의 화면 회전 기능과 운영체제의 방향 설정 고려하기.
- 실무 적용
    - 모바일 웹과 앱에서 세로모드/가로모드 모두 UI가 정상적으로 작동하는지 설계 및 확인하기.
    - 화면 방향이 바뀌어도 콘텐츠가 잘리거나 기능이 사라지지 않게 하기.
    - 화면 회전에 따라 버튼, 메뉴, 입력창 위치가 적절히 재배치되로록 하기.
- 예외 상황: 특정 모드가 고정된 서비스의 경우(피아노 앱, 은행 수표 작성, 특정 방향을 전제로 하는 콘텐츠 ex.VR)

1.3.5 입력 목적 식별(AA)
- 접근성: 개인정보를 입력하는 필드 중 WCAG에서 정의한 항목은 프로그램적으로 그 목적을 식별 가능해야함.
- 보조기술: 자동완성기능, 운영체제나 브라우저의 입력 지원 기능(저장된 정보를 적절한 필드에 제안)
- 실무 적용
    - 이름, 이메일, 전화번호, 주소 등 입력 목적을 명확하게 구분하기.
    - 각 입력 필드에 적절한 HTML [autocomplete] 속성을 적용하도록 개발자에게
    - 입력 필드의 라벨과 목적이 일치하도록 구성하기.
    - 사용자 정보를 입력하는 과정에서 반복 입력을 최소화!
