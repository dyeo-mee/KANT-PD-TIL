## 1. 컴포넌트 기반 개발
> 컴포넌트와 React가 무엇인지 설명 가능<br>
Props와 State를 Figma 컴포넌트 속성, Variant와 연결해 설명할 수 있다.

- 컴포넌트: 화면을 이루는 재사용 가능한 부품 → 웹/앱 화면에서 컴포넌트 단위로 만들고 조립.

- React: UI를 컴포넌트로 관리하는 JavaScript 라이브러리
    - 컴포넌트: 다시 쓰는 화면 조각
    - State: 바뀔 수 있는 값(상태)
    - 렌더링: 상태를 반영해 화면을 변경<br>
    → 화면 UI만 관리하고 실제 페이지 이동, 서버 통신은 다른 도구와 함께 사용

- JSX: JS안에 HTML처럼 쓰는 React 문법.

- Figma와 코드: 피그마 컴포넌트 속성과 코드 컴포넌트 입력값은 거의 같은 모양.<br>
→ 속성 이름 규칙을 코드와 함께 통일하기(팀 내 언어로)
    - Figma 컴포넌트의 variant(type, state), text, boolean
    ```
    <Button
        type="primary"
        state="default"
        label="예약하기"
        showIcon={false}
    />
    ```

## 2. Props와 State
- Props: 부모 컴포넌트가 자식 컴포넌트에 전달하는 값
- State: 컴포넌트 내부에서 관리하는 변경 가능한 데이터.<br>
✅ 리액트로 컴포넌트를 만들어 페이지 곳곳에 사용하면, 각각 다른 props를 전달받은 독립적인 요소가 됨.<br>
ex. 버튼의 이름은 props로 전달하고, 버튼 클릭 여부는 state로 관리.

- 컴포넌트 나누기: 여러 화면에서 반복해서 쓰이면 컴포넌트 후보.<br>
→ Figma와 코드의 컴포넌트, 속성 이름이 같아야 함.

## 3. Figma Dev Mode
- Dev Mode: 개발자가 디자인을 읽고 구현에 필요한 정보를 참고하는 Figma 화면<br>
→ annotation으로 주석을 달거나 inspect에서 에셋과 레이아웃 수치를 확인함.

- Inspect 패널: 레이어의 요소 정보를 보는 곳.<br>
    개발자는 바깥→ 안쪽, 배치 → 모양 순서로 읽음.

- 코드와 변수: 디자인 토큰을 변수로 입력하면 일일이 수정하지 않기 때문에 개발 효율이 올라감.<br>
    *→ 디자인 할 때 토큰의 이름이 중요한 이유*

- 에셋 내보내기

    | 에셋 | 형식 | 디자이너가 할 일 |
    |---|---|---|
    | 아이콘 | SVG | 벡터로 만들고 하나로 묶기(dev 모드가 찾아줌) |
    | 사진, 일러스트 | PNG, JPG(1x, 2x, 3x) | 고해상도 화면용 배율까지 수치 조정하기 |
    | 로고 | SVG | 글자는 윤곽선으로(outline stroke로 면 만들기) |
    | 복잡한 그래픽 | SVG, PDF | 쪼개진 레이어 정리 |

    → Outline stroke: 아이콘이나 글자의 크기를 바꾸면 비율대로 늘거나 줄어야하는데 깨주지 않으면(면이 아니면) 일정한 비율로 늘어나지 않는다.

- 개발 준비 표시 남기기
    - Ready for dev: 개발 시작해도 된다는 뜻 </>
    - 주석과 측정: 화면에 안 보이는 규칙은 주석으로. 화면에 있는 요소는 측정값 추가하기.
    - Ready for dev 이후 디자인이 변경된 상황
        1. dev mode에 수정된 내용 표시하기
        2. compare changes: before/after 나란히 비교하기
        3. 바뀐 내용으로 코드 구현

## 4. 디자인 핸드오프와 협업 트렌드
> 개발자가 디자이너에게 가장 많이 물어보는 것은?
- 핸드오프: 디자인을 개발로 넘기는 일.
    1. 기획 같이 보기: 구현 가능성 확인
    2. 시안 공유: 개발 난이도 확인하기
    3. 핸드오프: 체크리스트 전달
    4. 개발 중 대응: 질문이나 변경사항 공유 및 조정
    5. 디자인 QA: 시안과 동일한 화면이 나왔는지 확인<br>
    → 파일을 넘기고 끝내는 게 아닌, 개발자와 함께 처음부터 끝까지 의견을 조율하고 개선해가는 과정임.

- 자주 받는 질문들
    - 긴 글의 줄임 기준: truncate line을 몇 줄까지?
    - 로딩 중 혹은 비어있는 화면의 모습은?
    - 태블릿 등 브레이크 포인트 별 화면 변동은?
    - 색상에 대한 변수 존재 여부
    - 누르면 이동하는 화면의 흐름
    - 아이콘 다운로드 받는 위치 공유

- 핸드오프 체크리스트

    | 항목 | 내용 | 어디에 |
    |---|---|---|
    | 화면 흐름 | 화면 순서, 분기 | 흐름 섹션과 화살표 |
    | 상태 | 로딩, 빈 화면, 오류, 버튼 상태 | 상태 section |
    | 스펙 | 크기, 간격, Auto Layout | Dev Mode Inspect |
    | 컴포넌트 | 이름, props, state | 컴포넌트에 주석 |
    | 토큰 | 색, 글자, 간격 변수 | Variables |
    | 에셋 | 아이콘, 이미지 | Export 설정 |
    | 인터랙션 | 전환, 애니메이션 | 프로토타입과 주석 |
    | 접근성 | 대체 텍스트, 포커스 순서 | 주석 |

    → 사용자 흐름대로 화면 순서 배치하기<br>
    → Inspect에서 확인할 수 없는 내용은 annotation 달기
    > 💡 도구가 바뀌어도 결국 잘 정리된 구조가 가장 좋은 핸드오프.

- 디자인 QA: 개발된 화면이 디자인대로 만들어졌는지 확인하는 단계.
    - 시안 화면과 구현 화면을 나란히 비교
    - 기록 - 스크린샷 , 다른 점, 기댓값
    - 개선 우선순위 정하기

- 협업 트렌드
    1. MCP 서버: AI 코딩 도구가 Figma 레이어, 변수, 컴포넌트 정보를 읽어옴.
    2. Code Connect: Figma ↔ Dev Mode 
    3. AI 화면 생성: Figma Make에 프롬프트를 넣어 동작하는 화면을 바로 만들어봄.

- 디자이너의 역할<br>
    : AI도 사람이 만든 파일의 구조를 읽고 결과물을 만들기 때문에 정리가 잘 된 파일과 프롬프트 일수록 사용자의 의도대로 결과물을 받아볼 수 있다.

    - 컴포넌트와 프로퍼티
        - variant: 인스턴스의 디자인 형태를 변경(ex.Type: primary, secondary)
        - text: 인스턴스의 텍스트 내용을 변경(ex. label)
        - instance: 다른 컴포넌트 요소를 연결/교체 (ex. 아이콘 변경)
        - boolean: 인스턴스의 표시 여부(ex. showIcon: true, false)
        - state: 인스턴스의 상태 변경(ex. State: enabled, pressed, disabled)

    - 리액트 컴포넌트와 이벤트
        - 컴포넌트: 화면에 어떤 UI를 그릴지 정하는 것.
        - props: 이벤트가 발생하면 컴포넌트에게 전달하는 값을 가진 역할.
        - state: 현재 상태를 기억했다가 이벤트가 발생하면 바뀌는 값.
