## 1. Main Component / Instance / Override
- 복제의 한계
    - 소프트웨어가 커지고 복잡해지면서, 다른 페이지에서 같은 UI를 수정하는 일이 번번히 발생.
    - 재사용, 유지보수, 협업을 쉽게 하기위해 컴포넌트 기능을 사용.

- Main Component (컴포넌트 만들기: *cmd+option+k*)<br>
→ 한 번 만들어 여러 곳에 쓰는 재사용 요소.
    - main 하나만 고쳐도 인스턴스들이 한번에 바뀜
    - 복제된 요소를 수정하다보면 당장 눈에 띄지 않지만 차이가 발생할 수 있음<br>
    → 디자인 효율 up
        <details>
        <summary>디자인 시스템 구축 시기</summary>
        프로젝트 특성과 팀 환경에 따라 다름.<br>
        - 선 구축의 장점: 일관성 유지, 효율성 증대, 장기적 유지보수에 이상적.<br>
        - 후 구축의 장점: 요구사항 불확실 한 경우, 프로토타입 빠르게 제작해야하는 상황은 역으로 시스템화 하는 것이 현실적인 선택.<br>

        - 대응 방안: 엄격한 완성본 보다, 재사용성과 활용성에 염두에 둔 유연한 관리에 초점.<br>
            1. 최소 스펙 정의: 핵심 컬러, 타이포그래피, 아이콘, 기본 버튼 정의<br>
            2. 점진적 확장: 프로젝트 진행에 따라 필요한 컴포넌트와 패턴을 점진적으로 추가.<br>
            3. 협업 강조: 기획자, 개발자, 디자이너 모두가 만들어가고 활용하는 것.
        </details>

- Main ↔ Instance
    - main을 고치면 인스턴스에 전부 반영됨
    - 인스턴스를 고쳐도 메인은 그대로
    - 인스턴스에서 부모 요소(main)를 찾을 때: 우클릭>main component>go to~

- Override(덮어쓰기)<br>
→ main을 고치더라도 인스턴스에서 직접 바꾼 값은 남음.
    - Override가 유지하는 것
        - 텍스트 내용
        - 글꼴, 채우기/선 색깔, 그림자/블러
        - 레이어 숨기기
        - 중첩 인스턴스 교체
    - 인스턴스에서 못 바꾸는 것
        - 레이어 순서/위치
        - Constraints(바꾸려면 Main component에서 가능)

- Reset / Detach
    - Reset<br>
    : 인스턴스 요소를 선택하고 오른쪽 패널 상단의 ‘more action’ > reset<br>
        → 인스턴스를 main 상태로 되돌리는 것.
    - Detach *(option+cmd+b)*<br>
    : 인스턴스와 main의 연결을 끊고 새로운 프레임으로 생성<br>
        → main 컴포넌트 디자인을 재활용 해 변형시킬 때 사용<br>
        → main 컴포넌트는 원본 자체이므로 instance만 detach 가능함!
        - UI 시스템을 제작하는 업무가 아닌 이상, main 컴포넌트를 다룰 일이 없음<br>
        신사업 등 새로운 프로젝트에서 컴포넌트의 형태 변형이 필요한 경우 인스턴스를 Detach해서 변형해 사용함.<br> 
        -> main 컴포넌트를 건들지 않도록 유의 ‼️

- 중첩 컴포넌트: 컴포넌트 안에 다른 컴포넌트의 인스턴스를 넣는 것.<br>
→ ex.카드 컴포넌트 안의 다른 컴포넌트 인스턴스인 버튼, 아이콘 요소
    - ***인스턴스 선택 후  오른쪽 패널에서 같은 분류의 인스턴스 요소를 선택 가능
    → swap instance***
    - 작은 부품(버튼, 아이콘)을 먼저 컴포넌트로 만들고 큰 부품(카드) 안에 넣는 게 실무 기본!

## 2. Variant 설계와 네이밍
- Variant property
    - 모양이 달라지는 이유를 속성을 기준으로 나눔

    | 속성(Property) | 뜻 | 값(Value) |
    |---|---|---|
    | Type | 버튼의 쓰임/중요도 | Primary, Secondary, Outline |
    | State | 사용자 행동, 가능 여부 | Default, Hocer, Pressed, Disabled |
    | Size | 놓일 자리, 크기 | S, M, L |

- Variant Metrix: Variant를 만들기 전, 필요한 속성과 조합을 설계하고 검토하는 도구.<br>
    - 설계가 필요한 이유
    1. 속성 정의: 어떤 요소가 달라지는지 먼저 분석. 무분별한 속성 추가를 방지.
    2. 속성 간 중복과 역할 충돌 방지: 하나의 속성이 명확한 역할을 담당하도록 설계.<br>
    한 축 안의 값은 중복되는 경우가 없어야 함.
    3. 불필요한 Variant 조합 줄이기: 속성과 값 개수는 곱셈으로 늘어나기 때문.
    4. 개발자와 디자인 구조 공유: 디자인과 개발에서 사용하는 속성의 의미를 일치시켜 업무 효율 up

- Combine as Variants → 컴포넌트를 2개이상 선택
    - 같은 속성을 공유하는 컴포넌트들을 모아 변수로 설정<br>
    ex. icon/heart, check, home, search
    - Variant 네이밍 규칙
        - 영어 명사 사용
        - Variant2 같은 기본 생성된 이름 사용금지. → 역할이나 목적이 드러나게 네이밍
        - 첫 글자는 대문자로 ex. primary ❌ Primary ✅<br>
        → 회사가 기존에 가지고있는 규칙을 따르는데 초점!
            <details>
            <summary> 피그마의 레이어명과 속성값을 개발 언어의 명명 규칙에 맞추는 이유</summary>
                - 디자인과 코드의 일관성을 유지 ⇒ 개발자와 디자이너의 해석 차이를 줄임<br>
                - AI 에이전트의 구조 이해도 향상(개발 자동화 및 코드 변환에 유리함)
            </details>

    - Instance Swap: 어떤 컴포넌트를 사용할 것인가?
        - 아이콘처럼 역할과 사용 방식은 비슷하지만 시각적 형태가 완전히 다른 요소를 교체할 때 사용
    - Variant: 같은 컴포넌트를 어떤 상태와 형태로 보여줄 것인가?
        - 버튼이라는 동일한 기능을 유지하면서 속성에 따라 디자인을 다르게 함.

    > 💡 Instance Swap = 같은 자리에 들어갈 다른 부품을 교체한다.<br>
    Variant = 같은 부품의 크기, 색상, 상태, 유형 등을 변경한다.

- 폭증과 슬래시 이름<br>
    - Variant 수 = 축마다 값 개수를 곱한 값.<br>
    : 축 하나가 생기면 수량이 급증하므로, 아이콘은 컴포넌트로 관리하지 않는다.<br>
    따라서, 아이콘의 경우 선택/비선택 으로 구분하고 Property로 관리함.

    - 슬래시(/) 이름<br>
        : 분류와 구조화를 위한 규칙. 컴포넌트를 어떤 카테고리에 속하게 할 것인가?<br>
        ```
        Icon/Home
        Icon/Search
        Icon/Heart

        Section/Hero
        Section/Body
        ```
