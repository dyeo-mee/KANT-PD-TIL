## 0. Prompt Engineering
AI가 사용자의 의도를 정확하게 이해하고 원하는 결과물을 생성하도록 입력값(프롬프트)을 설계하고 개선하는 기술.

> Prompt Engineering이 필요한 이유<br>
AI는 사람처럼 질문자의 의도를 완벽히 파악하지 못 함.

- 디자인에 적용하기
    - 프롬프트 핵심요소 6가지(역할, 맥락, 목표, 사용자, 제약조건, 예시(아웃풋))를 UI 화면 개선과 UX 라이팅을 하는데 사용해 작업물의 완성도를 높인다.

## 1. 디자인 맥락 프롬프트

> 레퍼런스를 특징 설명으로 프롬프트에 넣을 수 있음<br>
일정한 품질로 결과물 받는 법<br>
좋은 프롬프트를 지속적으로 사용하기 위해 필요한 요소 파악하기

#### 맥락 없는 요청

[ AI는 우리의 서비스, 사용자, 그 화면에서 무슨 일이 있었는지 모름 ]

- AI Literacy 2장 복습내용
    - 역할, 맥락, 과업, 형식, 제약, 예시 → 필요한 디자인 산출물에 맞게 요청하기

- 맥락 블록 3가지
    1. 서비스: 서비스 종류, 톤(말투)
    2. 사용자: 누가, 어떤 상황에서 문제를 겪는지
    3. 화면 상황: 어느 화면(지점)에서 일어나는 상황<br>
    ```xml
    [맥락 블록 예시]
    <content>
        <service>모임핏:동네 운동 클래스 예약 앱</service>
        <user>퇴근길에 짧게 앱을 켜는 20~30대 직장인. 빨리 예약을 끝내고 싶어함.</user>
        <screen>결제 버튼을 누른 직후, 카드 한도 초과로 결제 실패. 자리는 10분동안 유지됨.</screen>
    </content>
    ```

    - ***코드형식으로 프롬프트를 작성하는 이유***
        1. 정보 간 혼동 방지: 각 정보의 역할을 구분하기 쉽다.
        2. 복잡한 요청의 구조화: 요청사항이 많아질수록 작업의 우선순위와 조건을 파악하는데 도움을 줌.
        3. 수정과 재사용이 편리함: 기존 프롬프트에서 필요한 부분만 수정하고 재사용하기 용이함.

- 제약 조건과 레퍼런스
    - 제약 조건은 구체적인 숫자로 지시하기

        | 제약 | 모호한 프롬프트 | 수정한 프롬프트 |
        |---|---|---|
        | 길이 | 짧게 해줘 | 제목 15자, 본문 40자 이내 |
        | 말투 | 친근하게 | 해요체, 사과는 한 번만 |
        | 내용 | 잘 안내해줘 | 원인 1개 + 다음 행동 1개 |
        | 금지 | 이상한 말 빼고 | 오류코드나 "실패했습니다." 쓰지 않기 |

    - 레퍼런스 설명 → “OO 앱처럼 해줘” 말고 좋은 점을 특징으로 설명
        - 내가 만들고싶은 레퍼런스의 특징을 짚어서 알려주기<br>
        ex. 사용자를 탓하지 않고 다음 행동을 먼저 알려줘, 시간/금액은 숫자로 작성<br>
        → 디자인 시스템 링크나 화면 예시를 첨부해 만들어달라고 할 수 있음. 예시를 다양하게 입력해 비슷한 결과물만 생성하지 않도록 하기.

#### 화면 구성안
- 구성안 흐름
    1. 맥락 블록 작성
    2. 결과물로 받은 구성안 표 확인
    3. Figma로 옮기기: 구성안 표를 AI에 입력해 화면 제작 or 직접 제작
    4. 화면 기준 검토: 휴리스틱, 접근성, 컴포넌트 등 기준에 맞게 검수<br>
        ```xml
        [화면 구성안 프롬프트 예시]
        <content>
            <service>모임핏:동네 운동 클래스 예약 앱</service>
            <user>퇴근길에 짧게 앱을 켜는 20~30대 직장인. 빨리 예약을 끝내고 싶어함.</user>
            <screen>결제 버튼을 누른 직후, 카드 한도 초과로 결제 실패. 자리는 10분동안 유지됨.</screen>
            <task>결제 실패 화면의 구성안을 써줘. 위에서 아래 순서로</task>
        </content>
        ```
        - 화면을 바로 만들지 않고, 기획을 하게끔 설명.<br>
        → 구성안으로 받은 표를 화면으로 구현하면 와이어 프레임이 된다.

- 화면 캡처로 비평 받기<br>
    : 화면에 대한 비평을 받고 검수/개선해야할 점 리스트업
    - AI 비평 프롬프트에 들어갈 결과물 형식 예시
        1. 잘 설계된 부분 물어보기
        2. 발견한 문제점 찾기
        3. 문제가 발생하는 이유
        4. 구체적인 개선 방향
        5. 개선 우선순위 (높음/보통/낮음)

    - 검수할 때 주의할 점
        - 사실과 추측을 구분하기: 화면에서 실제로 확인할 수 있는 근거가 있는지 확인(화면에 없는 요소를 지어내지 않는지 등 검토)
        - 사용자 관점에서 검증하기: 실제로 서비스를 이용하는 사용자의 심리는 사람이 더 잘 파악하기 때문에 한번 더 사용자 관점으로 화면의 문제를 살펴볼 것.
        - 접근성과 사용성 기준 확인하기: AI가 디자인 비평에서 놓칠 수 있는 부분<br>
        → WCAG와 같은 접근성 가이드라인을 기준으로 실제 수치 확인해보기
        - 문제의 중요도와 개선 우선순위 판단: AI는 사소한 시각적 문제와 중요한 사용성 문제를 비슷한 비중으로 판단할 가능성이 있음.<br>
        → 사람이 직접 사용자의 목표 달성을 방해하는 문제의 우선순위를 판단해야함.

## 2. Few-show으로 품질 고정하기
> Zero-shot / Few-shot의 차이점<br>
AI가 예시를 베끼는 문제를 줄일 수 있음<br>
좋은 예시를 고르는 기준은?

#### Zero-shot vs Few-shot
- Zero-shot: 예시 없이 글로만 설명
- Few-shot: 설명과 함께 원하는 결과물 예시 2개<br>
→ 여러번 같은 프롬프트를 반복했을 때 비슷한 맥락의 결과가 나오는지 확인해보기

#### 좋은 예시 고르기
1. 실제로 쓸 수준 - 바로 써도 괜찮은 퀄리티가 나오는지 확인
2. 서로 다른 상황 - 다양한 케이스를 입력해도 기준을 지키는 답변을 하는지 확인
3. 같은 형식 - 제목, 본문, 버튼 구조를 통일해 원하는 패턴 구조를 학습시킴
- 피할 예시: 같은 상황에 대한 예시만 제공, 원인을 알려주지 않음

#### 예시를 베끼는 문제
- 예시가 하나뿐이거나 서로 너무 비슷하면 구조가 아닌 문장을 따라할 가능성이 높음.
    - 예시는 구조만 참고, 문장은 새로 만들것을 명시
    - 예시 상황을 2~3개로 다양하게 구성
    - 원인과 특징 목록을 따로 줌

- 반복 실행으로 확인하기
    - 한 번 잘 나온 것은 운 일수도 있음 → 좋은 프롬프트로 인해 나온 결과인지 확신이 적음.
        1. 같은 프롬프트를 5번 실행해보기
        2. 기준을 가지고 체크하기 (길이, 말투, 문장 구조, 톤)
        3. 벗어난 이유 찾기
        4. 다음 버전에 반영해 개선하기

## 3. 프롬프트 버전 관리
> 프롬프트 버전 관리가 필요한 이유<br>
버전마다 남길 4가지 정리<br>
팀 프롬프트 라이브러리 만들어보기

#### 프롬프트 버전 관리가 필요한 이유
1. 무엇을 바꿨는지 기억에 의존해야 함
2. 팀원이 같은 시행착오를 반복 함
3. 최종 선택한 결과물의 근거를 설명하기 어려움

- 버전 기록과 평가: 버전마다 남길 4가지
    - 변경 이유: 지난 결과의 문제 적기
    - 변경한 내용: 무엇을 더하고 뺐는지 적기
    - 결과 비교: 같은 기준으로 전/후 비교하기
    - 사용한 도구(날짜/버전): AI 도구의 버전마다 성능과 결과가 다르기 때문<br>
    → 프롬프트의 어떤 변경이 결과물의 품질을 개선하는데 효과있었는지 기록하고 추적하기 위함

- 같은 버전 프롬프트 반복 입력하기(LLM)<br>
: LLM은 다음에 올 토큰을 활률적으로 예측하고 생성하는 방식이기 때문에 동일한 프롬프트를 여러번 입력하고 예외 상황이 발생하는지 확인하는 것.
    - 반복 실행을 통해 확인하려는 내용<br>
    → 결과물의 품질이 일정하게 유지되는가?<br>
    → 필수 조건이 매번 충족되는가?<br>
    → 원하지않는 결과가 얼마나 자주 발생하는가?<br>
    → 특정 실행에서만 우연히 좋은 결과가 나온것은 아닌가?

- 테스트 케이스: 다양한 상황에서도 의도한 결과를 만들어내는지 확인하기 위한 입력 시나리오.

    | 구분 | 목적 | 예시 |
    |---|---|---|
    | 반복 실행 | 동일한 입력에서 결과가 안정적인가? | test01 5회 실행 |
    | 테스트 케이스 입력 | 다양한 상황에서도 올바르게 작동하는가? | test01 ~ test05 실행 |
    | 버전 비교 테스트 | 프롬프트 변경으로 품질이 개선됐는가? | v1과 v2에 동일한 test01 ~ test05 실행 |

#### 루브릭 기준으로 점수 매기기
결과물을 평가하기 위해 미리 정의한 평가 항목, 판단 기준, 수준별 성취 조건을 정리한 평가표

| | |
|---|---|
| **일반적인 평가** | 디자인이 깔끔한가?<br>사용하기 편리한가?<br>완성도가 높은가? |
| **루브릭을 활용한 평가** | 가독성: 텍스트와 배경의 대비가 충분한가?<br>정보 위계: 중요한 정보가 시각적으로 강조되는가?<br>사용성: 다음 행동을 사용자가 쉽게 이해할 수 있는가?<br>일관성: 버튼과 컴포넌트의 디자인 규칙이 일관적인가?<br>접근성: 다양한 사용자가 정보를 인식하고 조작할 수 있는가? |

- 루브릭을 사용하는 이유
    1. 평가자의 객관성 확보: 사전에 정한 기준을 중심으로 평가
    2. 평가의 일관성 유지: 여러 결과물을 동일한 기준으로 비교 가능(디자인 초안 vs 수정본 비교)
    3. 부족한 부분 구체적으로 파악: 어떤 항목이 부족한지 확인
    4. 개선 방향 도출: 평가 항목별로 점수를 매겨 다음 작업에서 무엇을 수정해야할지 명확해짐.
    5. AI 평가 신뢰도 개선: AI에게 구체적인 평가 기준을 제공해 기준에 근거한 피드백을 받을 수 있음.

- LLM-as-a-Judge: AI가 매긴 점수는 후보. 사람이 직접 확인하고 판단한 점수만 기록할 것.
    - 루브릭 기준 + 결과 넣기(결과를 낸 도구와 다른 도구에 평가 맡기기)
    - AI의 점수와 이유 한 줄을 케이스별 표로 받기
    - 사람이 비교(가장 높은 점수, 가장 낮은 점수)
    - 확정 점수 기록

#### 프롬프트 라이브러리
- 템플릿 만들기: 어느 상황에서나 사용 가능한 템플릿을 미리 만들어 내용만 바꾸면 체계적이고 효율적인 결과물을 받아볼 수 있음
    ```xml
    [UX 카피라이팅 템플릿 예시]
    <context>
        <service> {서비스 이름 · 한 줄 설명 · 말투} </service>
        <user> {누가 · 어떤 상황에 놓여있는지} </user>
        <screen> {어느 화면 · 직전에 일어난 일} </screen>
    </context>
    <task> {문구 종류}를 {##} 세트 작성해 줘. </task>
    <constraints> {기기 종류}, 제목 {n}자 · 본문 {n}자 · {말투} · 금지: {쓰지 않을 말} </constraints>
    <examples> 좋은 예 {2~3개} / 피할 예 {1개 + 이유} — 예시는 구조만 참고, 문장은 새로 </examples>
    <format> 표: 제목 | 본문 | 버튼 | 글자 수 </format>
    ```

- 팀 프롬프트 라이브러리: 팀이 함께 쓰는 프롬프트 목록을 만들어 AI 사용 효율을 높이고 발생한 문제와 궁금증을 빠르게 해결 가능.
    - 라이브러리 예시

        | 이름 | 용도 | 최신 버전 | 담당 | 기록 |
        |---|---|---|---|---|
        | 결제 실패 문구 | UX 카피 | v3 | 팀원 A| *버전 기록 링크* |
        | 경쟁 앱 조사 | 리서치 | v2 | 팀원 C| *버전 기록 링크* |

    → 하면서 느낀 점
    - 재사용 가능한 프롬프트 템플릿을 작성하고 버전 기록을 할 수 있게됐다.
    - AI에게 맡길 루브릭 평가의 기준을 세우고, 결과로 나온 점수를 논리와 기준에 근거해 평가할 수 있게됐다.
