## 1. 웹접근성과 WCAG 2.1 AA
> 웹 접근성이 필요한 사용자와 상황을 설명할 수 있다.<br>
WCAG 4대 원칙과 AA 기준을 설명할 수 있다.

#### Web Accessibility: 누구나 서비스를 쓸 수 있게 만드는 것.
-  영구적, 일시적, 상황적 상황 때문에 불편한 모든 사람을 포함. (ex. 수술, 장애, 환경)

- 보조 기술 (Assistive Technology): 사용자는 다양한 보조 기술로 화면을 씀. 디자인에 기술을 반영해야 함.

    | 보조 기술 | 하는 일 | 디자이너가 챙길 것 |
    |---|---|---|
    | 스크린리더 | 화면의 글자, 버튼을 읽어줌 | 이미지 대체 텍스트, 아이콘 버튼 라벨 |
    | 화면 확대, 큰 글씨 | 글자와 화면을 크게함 | 글자 200%에도 잘리지 않게 레이아웃 조정하기 |
    | 키보드, 스위치 | 손 대신 키로 이동, 선택 | 포커스 순서와 표시 남기기 |
    | 색 보정, 고대비 | 색을 바꾸거나 대비를 높임 | 색에만 의존하지 않고 아이콘, 라벨과 함께 의미를 정확히 전달하기 |

- 4대 원칙 WCAG: W3C가 만든 웹 콘텐츠 접근성 지침.
    - 인식의 용이성(Perceivable) - 콘텐츠와 정보를 인식할 수 있어야 함.
    - 운용의 용이성(Operable) - UI를 조작하고 이용할 수 있어야 함.
    - 이해의 용이성(Understandable) - 콘텐츠와 UI의 작동 방식을 쉽게 이해 가능함.
    - 견고성(Robust) - 보조 기술에 맞게 안정적으로 동작해야함.

- 웹 접근성 등급 (현재 과목은 AA 기준으로 학습)

    | 등급 | 뜻 | 예시 |
    |---|---|---|
    | A | 최소 기준. 못 지키면 쓸 수 없는 사람이 생김 | 이미지 대체 텍스트, 색에만 의존 금지 |
    | AA | 대부분의 법, 기관이 목표로 하는 기준 | 명도 대비 4.5 : 1, 포커스 표시 |
    | AAA | 가장 엄격한 기준 | 명도 대비 7 : 1 |

#### 디자이너가 지킬 웹 접근성 기준
- 명도 대비: 글자와 배경의 명도 대비가 충분해야 함.
    - 본문 내용 = 4.5 : 1
    - 큰 제목 = 3 : 1 (24pt 이상)

- 색상 외의 정보전달: 색상만으로 정보를 구분하면 안됨.
- 터치 및 클릭 영역(Target Size): Web 24px, 모바일 44px 이상 터치 및 클릭 영역 확보.
- 글자 확대: OS 설정으로 글자를 확대해도 레이아웃이 깨지거나 내용이 가려져선 안됨.<br>
(글자가 확대는 200%를 기준으로 둠)
- 키보드 접근성: 마우스 없이 키보드(Tab 키)만으로 웹사이트를 이용 가능해야 함.
- 정보 구조 및 위계(Information Hierachy): 제목과 본문을 명확히 구분, 관련된 정보는 그룹화, 읽는 순서와 시각적 배치 순서 일치
- 폼과 오류 안내: 명확한 Label 제공, Placeholder 만으로 입력 목적을 설명하지 않기, 필수 입력 항목을 텍스트/기호로 명확히 구분
- Overlay: 썸네일 이미지가 밝은 색일 경우 위에 올라간 글씨가 잘 안보이는 상황이 생길 수 있으므로 오버레이(or Dimmer, Scrim)를 적용해 가시성을 높여줌.

- 대체 텍스트(Alt Text): 이미지, 아이콘 버튼 대신 읽어줄 글.<br>
→ 디자이너가 화면의 의도를 알기 때문에 미리 설계 후 핸드오프에 함께 적음.

## 2. 접근성 점검 연습
> 점검표의 내용을 전부 못고치는 상황에서 우선순위를 어떻게 선정해야할까?

#### 측정 도구
- 대비 측정: Figma에서 글자색과 배경색을 HEX 도구에 넣으면 대비율이 나옴. ***Check Color Contrast***<br>
    → Figma: 라이브러리 Color Generator에도 등급과 대비율이 존재함<br>
    → Figma 오른쪽 패널 Fill 옵션에서도 AA등급 여부에 적합한 색인지 확인 가능.

- 접근성 판정: 각 요소가 가진 대비율과 웹 접근성 기준을 놓고 판정 통과 여부를 확인

#### 점검표
    ✅ 점검은 수치와 판정으로, 수정은 막히는 것 우선으로 함.

- 점검 항목 6가지

    | 항목 | 확인 방법 | 기준 |
    |---|---|---|
    | 명도 대비 | 대비 측정 도구 | 본문 = 4.5:1 <br> 제목, UI = 3:1 |
    | 색 외 단서 | 흑백 화면 준비 | 상태를 색 뿐아니라 아이콘/글자로 함께 전달 |
    | 터치 영역 | 48x48 틀로 겹쳐보기 | iOS 44, Android 48 |
    | 포커스 | Tab 순서대로 번호 매기기 | 포커스 상태가 눈에 잘 띄고 정보 순서가 자연스러움 |
    | 대체 텍스트 | 이미지, 아이콘 버튼에 주석 달기 | 뜻은 짧게, 꾸미는 목적의 이미지 설명은 생략 |
    | 글자 확대 | 텍스트 200% 키우기 | 잘림/겹침 없음을 확인 |

- 수정 우선순위: 항목 심각도를 측정
    - 1순위 - 태스크가 막히는 것 ex.라벨없는 버튼, 대비 낮은 글자
    - 2순위 - 화면에서 자주 보는 것 ex.본문 회색 글자, 작은 터치 영역
    - 3순위 - 불편하지만 진행되는 것 ex.장식 이미지 대체 텍스트, 보조 정보 대비율

## 3. 디자인 시스템 사례 분석
- 디자인 시스템: 서비스를 만드는 원칙, 스타일, 컴포넌트, 사용 규칙을 한곳에 모은 것.<br>
⇒ 일관성, 속도, 협업

- 디자인 토큰: 디자인과 코드가 같은 값을 공유하게 하는 방식<br>
(색상, 간격, 폰트 크기, 굴곡 등)

- 4가지 구성
    - 원칙: 무엇을 중요하게 여기나
    - 파운데이션: 색, 글자, 간격, 아이콘, 굴곡, 그림자효과
    - 컴포넌트: 버튼, 입력칸, 카드, 배너
    - 가이드: 언제 어떻게 사용하는지 설명

- 공개 디자인 시스템

    | 디자인 시스템 | 만든 곳 | 특징 |
    |---|---|---|
    | Material Desing 3 | Google | Android의 기본, 컴포넌트/토큰/접근성 내용이 자세함 |
    | KRDS | 행정안전부 | 정부/공공 서비스용, 접근성 기준 포함 |
    | Polaris | Shopify | 쇼핑몰 관리자용, 상세한 문구 가이드 |
