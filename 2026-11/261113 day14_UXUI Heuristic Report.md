## 1. 10가지 휴리스틱
>화면 문제를 보고 위반한 원칙을 근거와 함께 짚을 수 있다.<br>
문제를 ‘불편해요’라는 표현말고, 근거를 기반한 문장으로 팀원들에게 이해하고 해결 가능하게 설명할 수 있다.

- 인상에서 진단으로<br>
    → 휴리스틱: 화면에서 사용성을 점검하는 진단 기준 목록
    
    - 사용성(Usability)<br>
    : 사용자가 특정 상황에서 제품/서비스를 이용해 목표를 효과적, 효율적으로 만족스럽게 달성 가능한 정도<br>
    → 사용자가 제품, 서비스를 얼마나 쉽게 이용할 수 있는가?

- 사용성 측정 항목
    - 효율성(Efficiency)<br>
    : 사용자가 서비스를 익인 후 얼마나 빠르고 적은 노력으로 원하는 작업을 수행할 수 있는가?
        - 측정 예시: 상품 구매까지 걸리는 시간
        - 측정 지표: 작업 완료시간, 클릭 횟수, 단계 수
    - 학습 용이성(Learnability)<br>
    : 사용자가 서비스를 처음 접했을 때 얼마나 쉽고 빠르게 사용법을 익힐 수 있는가?
        - 측정 예시: 신규 사용자가 회원가입을 얼마나 쉽게 완료하는가?
        - 측정 지표: 첫 작업 완료 시간, 도움말 사용 횟수, 성공률
    - 기억 가능성(Memorability)<br>
    : 한동안 서비스를 사용하지 않다가 다시 방문했을 때 사용법을 얼마나 쉽게 기억하고 활용할 수 있는가?
        - 측정 예시: 한 달 만에 방문한 사용자가 별도 안내 없이 상품을 구매할 수 있는가?
        - 측정 지표: 재사용 시 작업 완료 시간, 오류율, 도움말 의존도
    - 에러(Error)<br>
    : 서비스를 이용하면서 얼마나 자주 실수하는지, 얼마나 쉽게 복구 가능한지
        - 측정 예시: 회원가입 시 잘못된 이메일을 입력하거나 결제 단계에서 오류가 발생하는 경우
        - 측정 지표: 오류 발생 횟수, 오류율, 복구 시간
    - 만족도(Satisfaction)<br>
    : 서비스를 이용하면서 얼마나 편리하고 긍정적인 경험을 느끼는가?
        - 측정 예시: 서비스 이용 후 사용자가 전반적인 경험에 만족하는가?
        - 측정 지표: 만족도 설문, NPS, SUS 점수

- 사용성 확인하는 방법 (행동 - 태도)
    - 정성적: 사용성 테스트, 필드 관찰 - 사용자 인터뷰/포커스 그룹
    - 정량적: A/B Test, 로그/클릭 분석 - 설문조사
    - 휴리스틱 평가: 디자이너가 원칙으로 화면을 점검
    *→ 사용자없이 진행 가능하다는 장점*

> 💡 **어느 화면에서, 무엇이 문제였고, 사용자가 어떻게 행동했는지 알면 문제의 원인을 찾을 수 있음!**


- 휴리스틱 평가 (Heuristic Evaluation)<br>
***→ 휴리스틱 평가는 가설을 만들고, 사용성 테스트는 가설을 확인***
    - 사용성 문제는 5명의 참가자만 있더라도 85%정도 발견 가능하다(효율적)

- 10가지 원칙
    1. 시스템 상태 가시성: 서비스가 지금 무엇을 하고있는지 적절한 피드백으로 바로 알려줘야 함.<br>
    (버튼을 눌렀는데 아무 변화가 없음 → 사용자의 액션을 반영한 상태를 반영해주기)
    2. 현실 세계와 일치: 익숙한 언어와 현실과 같은 형태로 보여줘야 함.<br>
    (나쁜 예: 전문용어 노출, 회사 내부 언어 등 사용 → 사용자 문화에 맞는 단어와 문장)
    3. 사용 통제와 자유: 실수로 들어간 상황에서 빠져나올 수 있는 비상구(취소, 되돌리기)<br>
    (나쁜 예: 취소하려면 다른 메뉴로 가야함, 기억하기 어려운 경로를 제시함)
    4. 일관성과 표준성: 플랫폼이나 서비스 내부에서 일관된 디자인과 규칙을 유지<br>
    → 외부 일관성: 다른 회사의 서비스여도 플랫폼 및 업계의 관습을 따라 서비스 이해를 쉽게함<br>
    → 내부 일관성: 같은 서비스안의 레이아웃과 디자인을 일관성있게 제공
    5. 오류 예방: 친절한 오류 메세지보다, 애초에 실수가 생기지 않게 막는 디자인 설계가 먼저!<br>
    (ex. 마감된 선택지는 누를 수 없게 방지)
    6. 기억보다 직관: 앞 화면의 정보를 외우지 않아도 필요한 정보를 화면에 보여줘야 함.<br>
    → 지난 검색 기록을 미리 보여줘 사용자가 할 일을 떠올리는데 큰 에너지가 들지 않도록 함.
    7. 유연성과 효율성: 처음 쓰는 사람과 익숙한 사람 모두 빠르게 쓸 수 있게 지름길을 함께 둠.<br>
    (ex.매 주 같은 클래스를 예약할 때 바로 예약 가능한 선택지를 제공)
    8. 미니멀 한 디자인: 당장 필요없는 정보가 정작 필요한 정보를 가리지 않게 하는 것.<br>
    → 진정한 미니멀은 화면의 목적을 먼저 보이게 한다.
    9. 오류 인식/진단/복구: 오류가 나면 쉬운 말로 원인을 알려주고, 해결 방법을 함께 제안해야 함.<br>
    → 오류 문구에는 원인 + 다음 행동을 함께 나타낼 것
    10. 도움말과 문서: 설명없이 사용 가능한 상태가 가장 베스트. <br>
    하지만 설명이 필요하다면 문제를 마주한 순간 도움말을 바로 찾을 수 있어야 함.

- 헷갈리는 원칙의 기준

    | 비교할 원칙 | 구분 방법 |
    |---|---|
    | 5 오류 예방 vs 9 오류 복구 | 오류가 나기 전이면 5 오류가 발생한 뒤면 9 |
    | 3 통제와 자유 vs 5 오류 예방 | 오류를 예방하면 5 오류를 되돌리는 건 3|
    | 2 현실 일치 vs 4 일관성 | 사용자가 이해할 말과 순서는 2 앱 안이나 업계에서 이어지는 관례는 4 |

    ***→ 번호를 정확히 맞히기보다 "어느 화면, 무엇이 문제인지, 어떤 결과로 나타날지"를 찾고 설명할 수 있는게 중요함***

- 위반과 판단<br>
: 휴리스틱은 법칙이 아닌 판단 기준. 위반해도 상황에 따라 그대로 두기도 함.<br>
    ex. 모바일 앱의 햄버거 메뉴: 직관성은 위배했지만, 모바일 환경에 맞춰 요소를 숨겨둠.

> 💡 **원칙끼리 부딪힌다면, 주어진 상황에 따라 반대 급부는 어떤 상황과 리스크가 발생할지 예상하고 적절한 선택을 하는 것이 중요.**

## 2. 디자이너가 알아야 할 UX 법칙
> 피츠, 힉, 제이콥, 밀러의 법칙 알기<br>
게슈탈트 원리로 화면의 묶음 읽기<br>
화면의 설계 의도를 UX 법칙의 말로 설명해보기<br>

- 누르고 고르는 법칙
    - 피츠의 법칙: 목표까지 거리가 멀고 크기가 작을수록 누르는데 오래 걸림.<br>
    (Thumbzone - 엄지만을 사용해 닿는 화면의 영역)
        - 정보의 위계에 맞춰 적절한 영역에 배치하는 것이 중요.
    - 힉의 법칙: 선택지가 많고 복잡할수록 결정하는데 오래 걸림.
        - 선택지를 무작정 줄이는 게 아닌, 고르기 쉽게 정리하는 것이 핵심.

- 기억과 습관의 법칙
    - 제이콥의 법칙: 사용자는 대부분의 시간을 다른 서비스에서 보내기 때문에, 새 서비스도 익숙한 방식으로 움직이길 기대함.<br>
    → 꼭 새로워야 할 이유가 있는게 아니라면, 익숙한 방식을 따르는게 사용성에 유리하다.
        
    - 밀러의 법칙: 한번에 기억하는 양은 적으니, 정보를 덩어리로 나누면 기억하기 쉽다.<br>
    ex. 01012345678 → 010 1234 5678

- 법칙의 오해: UX 법칙은 지켜야 할 숫자 규칙이 아닌, 설계를 설명하는 근거

    | 법칙 | 생기는 오해 | 바른 적용 |
    |---|---|---|
    | 밀러 | 메뉴는 7개 이하로만 | 많은 정보는 덩어리로 나누기 |
    | 힉 | 선택지는 최대한 적게 | 분류를 우선 나누고, 추천하는 내용을 먼저 노출 |
    | 피츠 | 모든 버튼을 크게 제작 | 자주쓰고, 중요한 버튼만 크고 엄지와 가깝게 |
    | 제이콥 | 유명한 제품/서비스 디자인을 똑같이 따라 만들기 | 사람들에게 익숙한 패턴 위에 우리 서비스만의 차별점 더하기|

- 게슈탈트 원리: 개별 요소를 따로 인식하기 보다, 묶인 요소들을 하나의 의미로 인식하는 심리적 원리.
    1. 근접성: 가까우면 같은 그룹으로 인식한다. **거리*
    2. 유사성: 비슷한 모양, 색, 크기면 같은 성격이라고 인식한다. **비슷한 형태*
    3. 연속성: 끊어져 있는 요소라도 자연스럽게 이어지는 흐름이나 방향이 있으면 하나의 연속된 형태로 인식한다. **흐름*
    4. 폐쇄성: 불완전한 모습이어도 빈 부분을 채워 완전한 형태로 인식함. **완성*
    5. 전경과 배경: 시각 정보를 볼 때 자연스럽게 특정 대상을 전경으로, 나머지 요소는 배경으로 인식함. **대비*<br>
    ex.모달 창을 띄우고 배경을 어둡게 처리(중요한 콘텐츠와 배경의 시각적 대비 확보)
    6. 공동 운명: 다르게 생긴 요소라도 같은 방향으로 움직이면 하나의 그룹으로 인식함. **같은 움직임*
    7. 대칭과 질서: 대칭적이고 규칙적인 형태를 안정적이고 하나의 통일된 구조라고 인식하는 원리. **균형*

###  휴리스틱 평가 - 리포트와 심각도
> 찾은 문제 중 무엇부터 고쳐야 할까?

- 실제 사용자를 모집해 테스트하기 전에, 빠르고 적은 비용으로 치명적인 사용성 결함을 미리 발견하고 수정하기 위한 목적.
    - 평가 절차 4단계
        - 범위/태스크 정하기 - 어떤 화면에서 어떤 행동을 볼까?
        - 각자 평가 - 평가자 3~5명이 각자 평가함.
        - 합치기 - 겹치는 문제를 묶고 다른 의견을 확인함.
        - 심각도/개선안 - 무엇부터 어떻게 고칠지, 우선순위와 해결책 정하기.

- 범위와 태스크(Task: 사용자가 서비스에서 끝내려는 일)<br>
: 범위와 태스크가 없으면 평가를 합칠 때 혼란스러움 → 같은 기준으로 비교 불가능

- 유저플로우와 IA(Information Architecture)<br>
    : 평가할 화면은 태스크의 흐름(유저 플로우)으로 고르고, 앱 전체 지도(IA)에서 위치를 확인함.<br>
    - 사용자가 테스트를 예상대로 마침 → Happy pass<br>
    - 예상치 못한 구간에서 문제가 발생 → Edge case

- 평가지와 히트맵: 원칙마다 심각도(0~4)를 매기고, 팀 평균을 색으로 칠하면 어디를 먼저 손봐야 하는지 보임.
    - 심각도 등급

        | 등급 | 이름 | 의미 |
        |---|---|---|
        | 0 | 문제 없음 | 사용성 문제로 보기 어려움|
        | 1 | Cosmetic | 외관상의 사소한 문제, 우선순위가 낮음 |
        | 2 | Minor | 사용에 약간의 불편을 주는 문제 |
        | 3 | Major | 사용에 큰 불편을 주며 개선이 필요한 문제 |
        | 4 | Catastrophe | 서비스 이용이 불가능할 정도의 치명적인 문제 |

        -> 히트맵 색상이 빨갛다고 해서 무조건 심각한 문제는 아닐 수 있음.<br>
    활동이 집중된 영역이라는 의미도 존재해, 의도와 실제 행동을 함께 분석해야 함.

    - 심각도 판단 기준
        - 빈도: 얼마나 자주 생기는가?
        - 영향: 생기면 얼마나 영향이 생기는가?
        - 지속성: 한 번만 겪으면 추후 피할 수 있는 문제인가?

- 평가 리포트: 구성은 문제 1개 = 행 1개<br>
→ PM, 개발자가 읽고 바로 고칠 수 있게 씀.

    | # | 화면 | 문제(진단 문장) | 위반 원칙 | 심각도 | 개선안 |
    |---|---|---|---|---|---|
    | 01 | 결제 | 결제 버튼을 눌러도 3초간 변화가 없어 다시 누름 | 1 상태 가시성 | 4 | 누르면 바로 로딩 표시, 버튼 비활성화|
    | 02 | 마이 예약 | 예약 취소가 설정 메뉴 안에 숨어 있음 | 3 통제와 자유 | 3 | 예약 카드에 취소 버튼 두기 |

    - 화면 예시도 첨부해 최대한 구체적이고 알기 쉽게 한다.
    - 읽는 사람이 다시 묻지 않아도 되는지 생각해보기

- AI 초안 검증: 문제 후보를 빠르게 뽑지만, 화면에 없는 문제를 지어내기도 함.
    1. AI에게 후보 요청 → 화면 캡처 + 태스크 + 10가지 원칙
    2. 화면에서 확인 → 정말 화면에 존재하는 문제인가?
    3. 근거 붙이기 → 원칙, 심각도를 직접 생각해보고 작성
    4. 채택/삭제 → 근거없는 후보는 지우기

- ICE 방법론: 개선할 사항이 많을 때 제한된 시간과 자원을 어디에 투자할지 판단하는데 유용함.<br>

    [세 가지 평가 기준]<br>
    - Impact(영향도): 얼마나 큰 효과가 있을까?
    - Confidence(자신감): 얼마나 확신할 수 있을까?
    - Ease(실행 용이성): 얼마나 쉽게 실행할 수 있을까?

    → 각 항목을 1에서 10까지 점수를 매기고 평균을 계산.
    
- ICE 방법론의 장점과 주의점
    - 장점: 여러 개선 아이디어의 우선순위를 빠르게 정할 수 있다.<br>
    팀원 간 의사결정 기준을 통일할 수 있다.<br>
    영향도 뿐 아니라 실행 가능성까지 고쳐할 수 있다.
    - 주의점: 평가자의 주관적인 판단이 포함됨.<br>
    사용자 안전, 접근성, 법적 문제처럼 반드시 개선해야 하는 항목은 점수와 별개로 우선 처리해야 한다.
